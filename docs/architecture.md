# Architecture

How the GB Studio MCP server works internally. Read this if you want to contribute, add tools, or understand the codebase.


## How MCP Works

The [Model Context Protocol](https://modelcontextprotocol.io/) (MCP) is a standard for AI tools. This server:

1. **Starts** as a child process of the MCP client
2. **Communicates** over stdin/stdout using JSON-RPC 2.0
3. **Registers tools** that the AI can call by name
4. **Handles requests**: `tools/list` (enumerate tools) and `tools/call` (execute a tool)

The transport is **stdio** — the client writes JSON-RPC messages to the server's stdin, and reads responses from stdout. This is the simplest MCP transport; no HTTP, no ports, no auth.

## In-Memory State Model

The server is **stateful**. When you create or open a project, the entire `.gbsproj` JSON is loaded into a module-level variable in `src/project.ts`:

```typescript
let currentProject: GBSProject | null = null;
let currentProjectPath: string | null = null;
```

All tool handlers read from and write to this in-memory object. Changes are **not** automatically persisted — the user must call `save_project` to write to disk.

**Why stateful?** Because building a game is a multi-step process. You create a project, add scenes, add actors, wire up scripts — each step depends on the previous. Holding state in memory means each tool call is fast and doesn't require re-reading/writing the file.

**Trade-off:** If the server process crashes or restarts, unsaved changes are lost. The AI should call `save_project` frequently.

## Tool Module Pattern

Every tool module exports a `Record<string, Tool>` where each tool has:

```typescript
export const myTools = {
  tool_name: {
    description: "Human-readable description for the AI",
    inputSchema: {
      type: "object" as const,
      properties: {
        param1: { type: "string", description: "..." },
        param2: { type: "number", description: "..." },
      },
      required: ["param1"],
    },
    handler: async (args: { param1: string; param2?: number }) => {
      // Do work...
      return {
        content: [{ type: "text" as const, text: "Result message" }],
      };
    },
  },
};
```

Key conventions:
- `description` — shown to the AI so it knows when to use the tool
- `inputSchema` — JSON Schema for the arguments; the MCP client validates against this
- `handler` — async function that does the work; returns MCP content response
- Errors: throw an `Error` and `index.ts` wraps it in an error response

## How to Add a New Tool

1. **Decide which module** it belongs to (or create a new one in `src/tools/`)

2. **Add the tool** to the module's export:

```typescript
// src/tools/my_module.ts
import { requireProject } from "../project.js";

export const myTools = {
  my_new_tool: {
    description: "What this tool does",
    inputSchema: {
      type: "object" as const,
      properties: {
        myParam: { type: "string", description: "What this param is" },
      },
      required: ["myParam"],
    },
    handler: async (args: { myParam: string }) => {
      const project = requireProject();
      // ... your logic ...
      return {
        content: [{ type: "text" as const, text: `Done: ${args.myParam}` }],
      };
    },
  },
};
```

3. **Register the module** in `src/index.ts`:

```typescript
import { myTools } from "./tools/my_module.js";

const allTools = {
  ...projectTools,
  ...sceneTools,
  // ...
  ...myTools,  // Add here
};
```

4. **Build and test**:

```bash
npm run build
node test.mjs
```

## TypeScript Types

All types are defined in `src/project.ts`:

| Type | Description |
|------|-------------|
| `GBSProject` | Root project structure |
| `Scene` | A game scene/screen/room |
| `Actor` | An NPC or interactive object |
| `Trigger` | An invisible trigger zone |
| `ScriptEvent` | A script event (dialogue, conditional, etc.) |
| `Background` | Background image asset reference |
| `SpriteSheet` | Sprite sheet asset reference |
| `Variable` | Global game variable |
| `Palette` | Color palette |

## Test Suite

### `test.mjs` — Integration Tests (MCP Protocol)

Spawns the compiled server as a child process and communicates via the MCP protocol (JSON-RPC over stdio). Tests all 24 tools end-to-end:

```bash
node test.mjs
```

Tests: project creation → variable addition → scene management → actor CRUD → trigger CRUD → script events → save/validate → build → delete operations.

**26 tests total.** All must pass.

### `test-direct.mjs` — Direct Function Tests

Tests the tool handlers directly without the MCP protocol layer. Useful for faster iteration during development.

```bash
node test-direct.mjs
```

## Known Limitations

- **No asset file management** — backgrounds and sprites are stub references. Actual PNG files must be added via GB Studio's desktop app.
- **No collision editor** — the `collisions` array is stored but there's no tool to edit it. Use GB Studio's visual collision editor.
- **No music editor** — music tracks must be added via GB Studio.
- **Single project** — only one project can be loaded at a time. Opening a new project replaces the current one.
- **No undo** — operations are immediate. Use `get_scene`/`get_script` to inspect before making destructive changes.
- **State is ephemeral** — in-memory project is lost on server restart. Always `save_project`.
